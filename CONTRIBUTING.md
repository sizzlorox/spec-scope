# Contributing to spec-scope

Thanks for taking the time. This is a small, deliberately simple project — the fastest way to get a change merged is to keep it small and simple too.

By participating you agree to the [Code of Conduct](./CODE_OF_CONDUCT.md).

## Dev setup

Requires **Node >= 22**. There is no bundler, no framework, and no build step beyond `tsc`.

```bash
git clone https://github.com/sizzlorox/spec-scope.git
cd spec-scope
npm ci
npm run build
npm test
```

| Script                 | What it does                                  |
| ---------------------- | --------------------------------------------- |
| `npm run build`        | `tsc -p tsconfig.json` → `dist/`.             |
| `npm run typecheck`    | Same, no emit. Fastest correctness check.     |
| `npm test`             | Builds, then `node --test dist/test`.         |
| `npm run lint`         | ESLint over the repo.                         |
| `npm run lint:fix`     | ESLint with `--fix`.                          |
| `npm run format`       | Prettier, writing changes.                    |
| `npm run format:check` | Prettier in check mode. This is what CI runs. |
| `npm run clean`        | Delete `dist/`.                               |

Before you open a PR, the whole gate is:

```bash
npm run lint && npm run typecheck && npm test && npm run format:check
```

**`dist/` is never committed.** It's gitignored and generated by `npm run build`. If you see it in a diff, something has gone wrong.

## Project layout

`rootDir` is `.` and `outDir` is `dist`, so `src/x.ts` compiles to `dist/src/x.js` and `test/y.test.ts` to `dist/test/y.test.js`.

| Path                | Responsibility                                                              |
| ------------------- | --------------------------------------------------------------------------- |
| `bin/spec-scope.js` | Thin executable shim. Resolves and calls the CLI.                           |
| `src/cli.ts`        | Argument parsing and command dispatch. No business logic.                   |
| `src/detect.ts`     | Find the project root, identify the flavor, list dirs to scan.              |
| `src/parse.ts`      | Markdown → `SpecModel`. The only module that knows Markdown.                |
| `src/diagram.ts`    | `SpecModel` → `Diagram[]`. Pure, no I/O.                                    |
| `src/notes.ts`      | `NoteStore`: read/write `.spec-scope/notes.json`, long-poll, change events. |
| `src/server.ts`     | Local HTTP + SSE server.                                                    |
| `src/export.ts`     | Single-file HTML tech doc renderer.                                         |
| `src/vendor.ts`     | Resolves vendored Mermaid/Marked out of `node_modules`.                     |
| `src/types.ts`      | The shared data model. Read it first.                                       |
| `src/ids.ts`        | Stable, name-derived identifiers.                                           |
| `web/`              | Browser UI: `index.html`, `app.js`, `style.css`. Plain, no framework.       |
| `test/`             | `node:test` suites.                                                         |
| `docs/`             | Architecture and spec-format reference.                                     |

Two shared files are load-bearing for everything else: **read [`src/types.ts`](./src/types.ts) and [`src/ids.ts`](./src/ids.ts) before writing any code.** They define the whole data model and the id scheme.

### TypeScript rules that will bite you

- **ESM import specifiers must include the `.js` extension.** The project is `"type": "module"` with `moduleResolution: NodeNext`. Write `import { slug } from './ids.js';` — not `'./ids'`, even though the source file is `.ts`.
- `strict` and `noUncheckedIndexedAccess` are both on. Indexing an array gives you `T | undefined`. Handle it. Don't reach for `!` unless the case is genuinely unreachable, and if it is, say why in a comment.

### Style

2-space indent, single quotes, semicolons, 100-column print width, ES5 trailing commas. Prettier enforces all of it — run `npm run format` and stop thinking about it.

Comments should explain _why_, not restate the signature. Brief JSDoc on exported symbols. If you deliberately take a shortcut, mark it and name the upgrade path:

```ts
// tradeoff: single-pass regex; a real Markdown AST would handle nested emphasis.
```

## Running against a fixture

The fastest development loop is to point the CLI at a checked-in fixture project rather than a real repo:

```bash
npm run build
node dist/src/cli.js test/fixtures/openspec-project
node dist/src/cli.js test/fixtures/speckit-project --no-open
```

Fixtures live in `test/fixtures/<flavor>-<case>/` and are ordinary directory trees of Markdown — no scripting, no generation step. To add one, create the directory, add the Markdown files that reproduce your case, and reference it from a test. Keep fixtures minimal: the smallest tree that exhibits the behaviour, not a realistic project.

When you fix a parser bug, the fixture that reproduces it _is_ the regression test.

## Commits

This repo uses **[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)**. This is not a style preference — [release-please](https://github.com/googleapis/release-please) parses commit messages to decide the next version number and to generate `CHANGELOG.md`. A malformed commit message means a missing changelog entry or a wrong version bump.

```
<type>(<optional scope>): <description>

[optional body]

[optional footer]
```

| Type       | Use for                               | Version effect |
| ---------- | ------------------------------------- | -------------- |
| `feat`     | A new user-facing capability.         | minor          |
| `fix`      | A bug fix.                            | patch          |
| `docs`     | Documentation only.                   | none           |
| `test`     | Adding or fixing tests.               | none           |
| `refactor` | Behaviour-preserving code change.     | none           |
| `perf`     | A performance improvement.            | patch\*        |
| `build`    | Build system, tsconfig, dependencies. | none           |
| `ci`       | CI configuration.                     | none           |
| `chore`    | Anything else that isn't the above.   | none           |
| `revert`   | Reverting a previous commit.          | patch\*        |

Breaking changes get a `!` after the type and a `BREAKING CHANGE:` footer. Pre-1.0 that's a minor bump; post-1.0 it's a major.

\* `feat`, `fix` and breaking changes are what reliably drive a release. Whether `perf` and `revert` bump the version depends on release-please's release strategy, so if a change is something a user should receive in a patch, commit it as `fix` and don't rely on the distinction.

Useful scopes: `parse`, `diagram`, `notes`, `server`, `export`, `cli`, `detect`, `web`, `vendor`.

Examples:

```
feat(diagram): render GIVEN steps as Note over instead of an arrow

fix(parse): treat a scenario heading inside a fenced block as literal text

Fenced code in a proposal that documented the heading grammar was being
parsed as a real scenario, producing a phantom requirement.

docs: document the actor-annotation ceiling in the README

feat(cli)!: rename --wait to --timeout on the poll command

BREAKING CHANGE: `spec-scope poll --wait 300` is now
`spec-scope poll --timeout 300`.
```

## Branches

`<type>/<short-kebab-description>`, matching the commit type where it makes sense:

```
feat/task-flow-diagram
fix/windows-path-separator
docs/spec-format-reference
```

Branch from `main`. Rebase rather than merge to keep history readable.

## Pull request checklist

- [ ] `npm run lint && npm run typecheck && npm test && npm run format:check` passes locally.
- [ ] Commit messages follow Conventional Commits.
- [ ] Non-trivial logic ships with a `node:test` alongside it.
- [ ] New parsing behaviour ships with a fixture that demonstrates it.
- [ ] Public API changes are reflected in `docs/architecture.md`.
- [ ] New spec-dialect syntax is documented in `docs/spec-formats.md`.
- [ ] No absolute local paths, usernames, or email addresses anywhere in the diff.
- [ ] `dist/` is not in the diff.

CI runs Node 22 and 24 on Ubuntu, plus Node 24 on Windows. The Windows job is not decorative — this project does a lot of path handling and uses `fs.watch`, and both behave differently there. If your change touches either, expect Windows to be the job that fails.

### Tests

Non-trivial logic ships a test. We use the built-in `node:test` runner — no Jest, no Vitest, no assertion library beyond `node:assert/strict`.

```ts
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { parseMarkdown } from '../src/parse.js';

test('extracts an actor from an annotated WHEN step', () => {
  const doc = parseMarkdown(
    '### Requirement: Poll for notes\n\n' +
      '#### Scenario: Agent receives a note\n\n' +
      '- **WHEN** Agent: requests the pending notes\n',
    'spec.md'
  );
  assert.equal(doc.requirements[0]?.name, 'Poll for notes');
  assert.equal(doc.requirements[0]?.scenarios[0]?.steps[0]?.actor, 'Agent');
});
```

The pure functions — `parseMarkdown`, `classifyDoc`, everything in `src/diagram.ts`, everything in `src/ids.ts` — are the easiest and most valuable things to test. Prefer testing those over driving the server.

## Adding a new diagram generator

Diagram generation is pure: `SpecModel` in, Mermaid strings out. No file I/O, no async.

1. **Add the kind.** Extend `DiagramKind` in `src/types.ts`.
2. **Write the generator** in `src/diagram.ts`. Signature is `(input) => Diagram | null` — return `null` when there's nothing worth drawing (no requirements, no tasks, a single node). An empty diagram is worse than no diagram.
3. **Set the `anchor`** to the id of whatever the diagram describes — a `SpecDoc.id`, `Requirement.id`, `Scenario.id` or `SpecGroup.id`. This is what lets a reader attach a note to the thing the diagram is about, so getting it wrong is a real bug, not a cosmetic one.
4. **Build the id** with `diagramId(anchor, kind)` from `src/ids.ts`. Never hand-roll one.
5. **Escape every piece of user text** with `escapeMermaid()`. Spec text contains colons, semicolons, quotes, angle brackets and backticks, all of which are Mermaid syntax. This is the single most common source of a blank diagram panel.
6. **Register it** in `generateDiagrams()`.
7. **Test it** by asserting on the generated Mermaid source string. It's pure, so this is easy and there's no excuse.

Keep generated Mermaid readable — 4-space indent inside the diagram body, one statement per line. People do read it, and it ends up verbatim in exported tech docs.

## Adding support for another spec dialect

The parser is intentionally line-oriented and regex-driven. It is not a Markdown AST walker and doesn't need to be.

1. **Detection** — add the marker to `detectProject()` in `src/detect.ts`: the file or directory whose existence identifies the flavor, and the directories to scan. Add the flavor to `SpecFlavor` in `src/types.ts`.
2. **Classification** — teach `classifyDoc()` in `src/parse.ts` to map the dialect's filenames to a `DocKind`. This is a pure function of the relative path; keep it that way.
3. **Grammar** — extend `parseMarkdown()` to recognise the dialect's requirement and scenario headings. Everything must land in the existing `Requirement` / `Scenario` / `Step` / `Task` shapes. **If a dialect seems to need a new field on the model, say so in the issue before writing code** — widening the shared model affects the diagram generators, the web UI and the exporter all at once, and is the one change that isn't cheap.
4. **Fixtures** — add `test/fixtures/<flavor>-basic/` and assert on the parsed model.
5. **Document it** in `docs/spec-formats.md`, at the same level of detail as the existing dialects. That file is the reference a future contributor extends from; an undocumented dialect is a dialect nobody can maintain.

Diagram generators read the model, not the Markdown, so a correctly parsed new dialect gets every existing diagram for free. That's the whole point of the split.

## Reporting bugs and requesting features

Use the [issue templates](https://github.com/sizzlorox/spec-scope/issues/new/choose). For a parser bug, the single most useful thing you can include is the smallest Markdown snippet that reproduces it — that snippet becomes the fixture.

For security vulnerabilities, do **not** open a public issue. See [SECURITY.md](./SECURITY.md).
